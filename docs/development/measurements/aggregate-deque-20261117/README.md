# Aggregate Deque performance, 2026-11-17

Independent review found that the transfer temporarily retains up to half the original entries in addition to the original size. The final candidate falls back to the original rebuild when this would exceed `INT_MAX`; that enormous boundary was not allocated in testing. `candidate-guarded.hpp.txt` records the final header, `guarded-checks.json` the four compile/random configurations, and `guarded-results.json` the rerun. With the same CPU affinity and five-run median, the two opposite-end workloads were Clang 111.689→76.713 ms / 112.608→82.722 ms and MSVC 107.116→82.774 ms / 121.393→92.290 ms. The table below retains the original measurements before this guard.

Baseline: main `179d99a39514b3321a163218273b394cdf7e1203`, header blob `754cfb300e9f3e9392d09a2037ab741394967afd`. Candidate preserves the dynamic sequence and generic monoid. For trivially copyable and assignable S it transfers only the first half and repairs the remaining aggregates in place. Other types use the original temporary-vector rebuild. `prod()` returns the sole populated side without invoking `op`.

The [fastest submission 403007](https://judge.yosupo.jp/submission/403007) uses a contiguous allocation with an operation budget and in-place repair, fast I/O, and specialized modular affine evaluation. Its fixed budget and stronger type constraints differ from the public API, so its 11 ms submission is not a same-contract benchmark and is not copied. No assembly was introduced.

Windows Clang 18.0.3 (exact version in environment.json), MSVC 19.43, `-O2 -DNDEBUG` / `/O2 /DNDEBUG`, C++20, logical CPU 12 affinity, interleaved order, five runs. Separate end-to-end measurements compile the existing official verify program twice, using the same generated inputs and compiler, and include process launch, pipe input, formatted output and I/O. Five interleaved runs on CPU 12: large_max_00 595.46→540.80 ms; large_min_00 436.81→437.65 ms; large_triangle_00 441.76→446.35 ms; max_random_00 618.27→616.46 ms; random_01 460.07→459.45 ms. These are I/O-dominated Windows measurements; small differences are not evidence of improvement. Concurrent activity and CPU frequency are not controlled.

The existing Library Checker verify program was compiled with Windows Clang and run on all 16 official cases generated by the [official generators](https://github.com/yosupo06/library-checker-problems/tree/master/data_structure/deque_operate_all_composite); input and output SHA-256 values match the official hash.json after Windows CRLF normalization. Fixed-seed tests exercise 1..513 elements in each rebuild direction, one million mixed noncommutative operations, strings and a nonassignable value fallback under Clang gnu++20/23 and MSVC C++20/latest. `official-correctness.json` and `checks.json` retain results.

An exploratory test using a deleted move constructor failed compilation; it also fails with the baseline because its `vector<S>` rebuild requires moving S on this STL. `unsupported-results.json` retains a repeat for both versions. The test was corrected to a move-constructible, nonassignable value; no unsupported type claim is made.

The raw timing samples, compiler invocation and source snapshots are in this directory. To reproduce microbenchmarks on the measured Windows toolchain, copy the `*.txt` sources to their names without `.txt` and run `python run.py`; paths to the installed compiler, SDK and CPU affinity are specified there. Official test scripts likewise require the linked upstream generators, common/random.h and ACL headers.
