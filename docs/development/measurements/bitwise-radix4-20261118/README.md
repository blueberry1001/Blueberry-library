# ビット畳み込みの2段変換

main `4089073325823283c4558aaf7ce48a9070200f24` の header（Git blob `25da9f075a73d941c1ee1d7f9852cc47772b4c67`）を基準とした。XOR の Walsh–Hadamard 変換で隣接2段を同じ4要素に対して処理する。演算結果を `T` に変換できないが `T` へ代入できる型も使えるよう、中間値は要素からコピー構築し、各加減算の結果は要素へ代入する。長さ0・1・2の経路も維持し、積は従来どおり左入力と右入力の順で計算する。

AND／OR は非MSVC環境では元の単段変換と呼出し形を維持する。MSVC では4バイト以下の非整数型に限り、2段をまとめる。整数型と大きい型は単段変換を使う。追加の記憶領域と公開 API の型条件は変えない。

調査時の Library Checker 最速 [AND 409492](https://judge.yosupo.jp/submission/409492) および [XOR 409698](https://judge.yosupo.jp/submission/409698) は法998244353に特化し、SIMD・複数段変換・専用 I/O を使う。XOR は64bit遅延剰余、AVX2、radix-16 の生成アセンブリとキャッシュ分割を使う。これらは任意型の本 API と条件が異なり、提出コードそのものとの同条件の直接測定はしていない。本実装へのコピーや特定 ISA の必須化はしていない。高速提出との差と、GCC・競技サイトでの実行時間は未測定。

## 同条件の計測

Windows x64、Clang 18.0.3／MSVC 19.43、C++20、`-O2 -DNDEBUG` 相当、論理 CPU 16 に固定。同じソースドライバを版ごとに別バイナリとしてコンパイルし、固定 seed の同じ入力で呼出しを交互に実行。入力生成・I/O は計時外、入力コピー・構築・計算・全出力のチェックサムは計時内。warmup 1回、各9回中央値。共有CPUの負荷は制御できず変動が大きい。すべての比較でチェックサムは一致した。`results-split-confirm.json` に各回を収録する。

| 係数・操作・入力 | Clang 旧 | Clang 新 | MSVC 旧 | MSVC 新 |
| --- | ---: | ---: | ---: | ---: |
| modint AND、2^12 ×50回 | 2.743 ms | 2.458 ms | 20.049 ms | 15.828 ms |
| modint OR、2^12 ×50回 | 2.540 | 2.779 | 21.527 | 16.335 |
| modint XOR、2^12 ×50回 | 6.245 | 4.406 | 7.336 | 5.957 |
| modint AND、2^20 ×1回 | 20.452 | 20.368 | 218.340 | 169.481 |
| modint OR、2^20 ×1回 | 22.236 | 33.278 | 231.194 | 173.729 |
| modint XOR、2^20 ×1回 | 60.360 | 50.839 | 72.821 | 56.559 |
| uint64 AND、2^20 ×1回 | 30.883 | 32.910 | 53.147 | 51.861 |
| uint64 OR、2^20 ×1回 | 40.782 | 36.682 | 45.798 | 53.467 |

Clang の OR 2^20 は新旧とも同一の単段処理だが今回の中央値では大きな差が出た。旧は19.253〜44.581 ms、新は20.095〜42.907 msと各回が重複する。Clang `-O2 -DNDEBUG` で AND／OR の変換単体それぞれを新旧でアセンブリ化し、局所ラベル名を正規化した105命令がそれぞれ一致した。これは**変換単体**の比較であり、畳み込み全体の機械語や配置が一致したことを意味しない。共有負荷・呼出し側の配置を排除できず、要因を断定できない。別の5回比較では AND 2^20 が旧24.852／新29.956 ms、OR が旧22.714／新20.657 ms、XOR が旧61.085／新46.516 msだった。`results-split.json` と `codegen-and.s`、`codegen-or.s` を参照。

比較には小さい入力・標準整数も含め、全型を一律2段化する案、2入力を同時に変換する案、ACL固定modint向け64bit遅延剰余、全環境でAND／ORを単段に戻す案、MSVC限定案を試した。2入力同時変換は64bit係数で遅く、遅延剰余はClangの2^20 XORで改善が小さい一方で一時メモリが増えたため採用しなかった。AND／ORの全型2段化もMSVCの一部整数入力で回帰した。棄却案の測定を含め `results*.json` に保存する。初期の `results1.json` などは試行中にdriverを更新したため、その時点のdriver原本は保存できていない。最終版のdriverとコマンドは `compare-split.cpp`、`run-split.py`、`run-split-confirm.py` にある。

## 正答性・再現

- Clang／MSVC × C++20／23 × debug／release で、空・長さ1・2・4から256まで、modint998244353・3・7、符号付き／符号なし整数、double を愚直畳み込みと比較した。
- コピー構築可能・コピー代入不可で、加減算結果から T への暗黙変換もできない代入専用型を旧版・新版で検証。非可換2×2行列でも積の順序と3種の結果を愚直解と比較した。
- 独立監査で N=0,1,2,4,8,16 の代入専用型と非可換行列を追加比較。Clang／MSVC × C++20／23で成功。`validation.json`、`validation-baseline-proxy.json` に自分の実行ログを保存した。
- 最終ヘッダ単独を ACL include path なしで Clang／MSVC でコンパイル・実行した。公式 Library Checker の実ケースと GCC は統合後の CI で確認する。

生ログ・driver・候補原本・最終テスト・アセンブリと検証コマンドを `reproducibility.tar.gz` に保存した。`archive.sha256` は圧縮ファイルの SHA-256。展開後は各スクリプト内のコンパイラ、Windows SDK、ACL のパスを環境に合わせて変更し、別の作業ディレクトリで実行する。

独立監査の試験・実行記録は `independent-audit/` にある。最終ヘッダの Git blob は `15c1d43f586492ad5972e6eeb751fe42637d4e25`。
