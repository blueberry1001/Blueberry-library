# 最長増加部分列の性能比較

基準は main `4089073325823283c4558aaf7ce48a9070200f24` の `longest-increasing-subsequence.hpp`（Git blob `fbf5963b2f4ecbbabdb2ff877f049e42707f36c4`）。[Library Checker 最速提出 #372659](https://judge.yosupo.jp/submission/372659) は整数値の末尾候補を連続配置し、末尾への追加を先に試し、各位置の長さから逆走査で解を復元する。提出は `uint32_t` 固定と専用 I/O を使う。比較対象は同じ汎用APIに適用した独立実装で、提出ソースそのものの同一条件測定ではない。

整数型では比較対象を連続した値配列に置いて間接参照を省く。各位置で終わる最長長を記録し、末尾から必要な長さを順に選んで復元する。MSVC は分岐の少ない二分探索、Clang と GCC は `std::lower_bound` を使う。整数以外、`bool`、64bitを超える型には従来の添字・前駆配列を使用する。元と同じ `<` のみの契約、コピー不可の独自型、空入力と同値の扱いを維持する。整数の補助配列は最大で値N個とint N個、加えて返却配列であり、64bit値では旧版の添字配列より最大4Nバイト増える。確保量の実測は行っていない。

Windows 11、Intel Family 6 Model 183、論理 CPU 4 に固定。Windows Clang 18.0.3 `-std=gnu++20 -O2 -DNDEBUG`、MSVC 19.43 `/std:c++20 /O2 /DNDEBUG`。同一バイナリ・同一入力で旧実装と最終版の順番を交互に変更し、warmup 1回の後7回測定した中央値。入力生成と I/O は計時外、構築・復元・返却配列の生成は計時内。N=200000、同じ入力に対する3呼び出し合計、単位は ms。共有マシンの他の負荷は制御していない。

初期の9候補と11候補の探索、Clang/MSVC別の結果および最終版はアーカイブ内の各 `result*.json` と `public-result.json` に残す。分岐を減らした探索は MSVC の乱数で速かったが、Clang では標準の探索より遅くなる分布があったため、コンパイラごとに選択した。GCCでの性能、最速提出の直接比較、公式入力の構築・I/O・ピークメモリを含む時間は未測定。

50,000件の固定seed乱数を二乗時間の愚直解と比較し、値と添字の厳密増加を確認した。公開テストは int・uint64 の重複、int64両端、`vector<bool>`、`string`、コピー不可型も含む。公開ヘッダのテストは Clang / MSVC × C++20 / 23 で成功。

独立監査では int8・uint8・int32・uint64 の4値列を長さ0〜8で全列挙した349,524列について、二乗DPと復元結果を比較した。int64全域乱数、両端値、`vector<bool>`、コピー不能かつ明示的なbool変換を返す比較型も加え、Clang / MSVC × C++20 / 23 で成功した。試験と実行記録は `independent-audit/` にある。

4ライブラリの統合状態で各公開テストを再実行した記録は `integration-results.json` と `integration-run.py.txt` にある。

`reproducibility.tar.gz` は基準・候補・ドライバ・全生ログ・検証コードを含む。`archive.sha256` で圧縮ファイルを照合できる。各 runner のコンパイラパスを環境に合わせて再実行する。試行段階の結果は、`candidates.hpp` 内の対応する候補と過去のループ条件を使用した。
