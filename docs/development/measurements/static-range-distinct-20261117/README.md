# StaticRangeDistinct 構築の候補調査

2026-11-17 に、順序同値を `operator<` だけで判定するオンライン問い合わせ API を維持した候補を比較した。ACL に相当する標準実装はない。[Library Checker の実行時間順一覧](https://judge.yosupo.jp/submissions/?order=%2Btime&problem=static_range_count_distinct&status=AC) では、取得時点で [363615](https://judge.yosupo.jp/submission/363615) が 49 ms で最上位だったが、提出ソースの取得は失敗したためアルゴリズムを確認できていない。提出時間を本測定と直接比較しない。既存調査の offline Fenwick は問い合わせを先読みするため同じ API ではない（[関連記録](../../batch-three-ds.md)）。

変更前の map を用いる直前位置計算と、同じ WaveletMatrix を使う候補を比較した。`sort` は要素値順、同値の場合は元添字順に添字を並べる。`hybrid512` / `hybrid2048` は異なる値がそれぞれ 513 個 / 2049 個に到達した時点で添字ソートへ切り替える。`radix` は bool 以外の整数型について、符号付きの最上位ビットを反転した符号なしキーで安定 LSD radix sort を行い、それ以外は map を用いる。

コンパイラは Unity 付属 NDK Clang 18、Windows MSVC ABI、`-std=gnu++20 -O2 -DNDEBUG`。CPU affinity を 1 論理 CPU に固定し、同一 seed・入力についてウォームアップ後に順序を交互に入れ替えて各 5 回測った。構築と 2 万件の問い合わせを分け、process peak working set も記録した。各実行の値とチェックサム、入力分布、環境、ソースの SHA-256 は JSON に保存している。チェックサム一致は全問い合わせの個別比較ではなく、別途 assert 有効で全区間と乱択区間を set と比較した。取得済みファイルの一部は `.txt` として保存している。

保存した測定ドライバは `GetProcessMemoryInfo` が失敗した場合に peak working set として 0 を出力する。再利用時、この 0 はメモリ使用量ではなく欠測値であり、その実行をメモリ測定成功として扱わない。保存済み JSON の各計測サンプルに 0 は含まれていない。

| 50 万件・構築中央値 | baseline | sort | hybrid512 | hybrid2048 |
|---|---:|---:|---:|---:|
| int 全幅ランダム | 217.922 ms | 55.930 ms | 56.575 ms | 58.443 ms |
| int 昇順 | 66.135 ms | 5.800 ms | 5.527 ms | 5.822 ms |
| int 2048 種類 | 42.455 ms | 72.543 ms | 73.583 ms | 42.176 ms |

各閾値の少し上では低重複でなくてもソートへ移り、回帰するため採用しない。32/64 bit 整数の純 radix は、同じ CPU・コンパイラでの別計測で以下の結果だった。

| 50 万件・構築中央値 | baseline | radix |
|---|---:|---:|
| 32 bit 全幅ランダム | 268.163 ms | 14.895 ms |
| 32 bit 全要素同一 | 15.784 ms | 21.681 ms |
| 64 bit 全幅ランダム | 276.711 ms | 18.424 ms |
| 64 bit 全要素同一 | 15.280 ms | 28.603 ms |
| 64 bit 8 種類 | 24.772 ms | 34.382 ms |
| 64 bit 符号付き極値の混在 | 21.497 ms | 31.534 ms |

純 radix の小さい値域での回帰は無視できず採用しない。bool の proxy、大小同値の異なるオブジェクト、整数の各符号・幅・極値および空区間についても独立のテストを実行した。初回のテストソースは後から復元し、保存済み JSON の SHA-256 と一致することを確認している。別の閾値付き radix 候補は引き続き評価する。

次に、異なる値が 2049 個に達するまで map を用い、その後は整数型のみ radix に切り替えた。問い合わせチェックサムと独立の正誤テストは通った。

| 50 万件・構築中央値 | baseline | radix 切替 |
|---|---:|---:|
| 32 bit 全幅ランダム | 207.788 ms | 13.540 ms |
| 32 bit 2049 種類目が末尾 | 45.644 ms | 53.469 ms |
| 64 bit 全幅ランダム | 250.038 ms | 17.247 ms |
| 64 bit 2049 種類目が末尾 | 45.820 ms | 61.280 ms |

末尾での切り替えにより、map で処理済みの全入力に対して radix の処理を追加するため回帰した。この切替条件は採用しなかった。復元したベンチマークソースは `radix-hybrid-results.json` の SHA-256 と一致した。

そこで、2049 種類目が先頭から N/8 個未満の位置で見つかったときだけ切り替える案を作り、少数種類と終盤での回帰を抑えた。公開ヘッダはこの案を反映している。最終ヘッダを使う再計測の中央値は以下のとおり。

| 構築時間 | baseline | final |
|---|---:|---:|
| 50 万・32 bit 全幅ランダム | 186.989 ms | 13.190 ms |
| 50 万・64 bit 全幅ランダム | 237.050 ms | 16.698 ms |
| 50 万・32 bit 切替位置の直前 | 48.161 ms | 40.322 ms |
| 50 万・32 bit 切替位置の直後 | 46.057 ms | 45.513 ms |
| 50 万・64 bit 切替位置の直前 | 49.762 ms | 47.745 ms |
| 50 万・64 bit 切替位置の直後 | 49.983 ms | 49.274 ms |
| 2 万・32 bit 4096 種類 | 2.164 ms | 2.699 ms |

小入力 4096 種類の再計測は約 25% 遅く、独立した先の候補計測では 2.056 → 2.064 ms だった。測定に揺れがあり、この入力について改善を主張しない。境界直前・直後、半分・末尾で 2049 種類目が現れる入力、同一値、少数種類、昇順・降順、整数極値を混ぜた入力も測り、全サンプルを `radix-limited-results.json` と `final-results.json` に残した。計測は構築を含む局所ベンチマークであり、公式問題全体の実行時間を意味しない。

変更後の `tests/random/ds_batch_three.cpp` は Clang 18 / MSVC ABI の `gnu++20`、`gnu++23` ともに `-O2`、assert 有効、seed 1、17、731 で通過した。bool の proxy、`operator<` だけの独自型、符号あり 16/32/64 bit の切替境界、符号なし 64 bit の極値と重複を含む。別の測定用テストでは 8/16/32/64 bit の符号あり・なしの極値についても set と比較した。`git diff --check` は通過した。

この Windows 環境では `make` と GCC が PATH 上になく、WSL は `Wsl/E_ACCESSDENIED` だったため、GCC、`make check` / `make test` / `make verify` / `make docs` と公式問題実行は未実施。保存した `final-compile.py.txt` は `.build` 内に比較用旧版を置くためのローカルスクリプトであり、再実行時は本フォルダの `baseline.hpp.txt`、`wavelet-matrix.hpp.txt` とドライバをスクリプトの指定する位置に配置する必要がある。

最初の [CI 実行](https://github.com/blueberry1001/Blueberry-library/actions/runs/44038548600) は、`-Werror -Wshadow` で構築処理内の変数名の重複が検出され失敗した。公開ヘッダの外側の添字変数を `i` から `pos` へ改名して修正した。これは識別子のみの変更であり、保存済みの測定用スナップショットは変更していない。

改名後、Clang 18 / MSVC ABI の `gnu++20`、`gnu++23` それぞれで `-O2 -Werror -Wshadow` を指定して `tests/random/ds_batch_three.cpp` をコンパイルし、seed 1、17、731 で通過した。GCC による再確認は CI で行う必要がある。

## 4096 種類の再計測

2 万件・4096 種類の 25% 回帰を調べるため、上記と同じビルド済みバイナリ・入力・コンパイラ設定を使い、同じ CPU に固定してウォームアップ 2 回後に変更前後を交互に 41 回ずつ計測した。構築時間の中央値（最小–最大）は、32 bit が 2.0782（2.0006–2.2244）→ 2.0848（1.9851–3.3725）ms、64 bit が 2.1093（1.9602–3.0021）→ 2.1236（1.9605–2.5946）ms だった。前回の約 25% の差は再現しなかったが、最大値のような外れ値もあり、環境や実行ごとの変動は残る。この結果は他の分布や環境で回帰がないことを保証しない。

全サンプル、バイナリと入力ソースの SHA-256、および実行条件は `rerun-4096-results.json`、計測スクリプトは `rerun-4096.py.txt` に保存した。旧版・最終版ヘッダ、共通 WaveletMatrix、およびベンチドライバの SHA-256 は上記の `final-results.json` と一致する。メモリ値が取得できなければスクリプトは失敗として停止する。
