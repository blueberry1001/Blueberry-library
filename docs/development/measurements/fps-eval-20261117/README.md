# FPSの単一点評価の測定（2026-11-17）

`FPS::eval`と`operator()`は、公開契約のACL素数法`static_modint`で多項式を評価する。係数を4剰余類に分けてHorner法で独立に評価し、最後にまとめる。小入力は単純なHorner法、0・1項は直接返す。空の多項式の値は0で、時間O(N)、追加領域O(1)は変わらない。可換な剰余環の分配則を使うため、任意の非可換な係数型への一般化ではない。既存の多点評価の末端もHorner法を使う。最速提出の単一点評価との比較は行っていない。

## 試作

`grouped.cpp.snapshot`は旧式、単純なHorner、2系列、4系列の比較。旧式は昇順で冪を作り、2系列・4系列はそれぞれ添字の剰余類を独立にHorner評価する。同じプロセス構成、ランダム係数・評価点、計算結果のchecksumを使った。長さ0〜499、各30点で全候補の値が一致した。旧式・単純Hornerの先行測定 `results-horner.json` は独立した小試作であり、実行コードのsnapshotがないため参考値に限る。

`results-grouped.json`は各条件warmup 1回と7回、順序を入れ替えた全生値を記録する。Windows Clang、O2 releaseでN=256・2万点の中央値は旧式14.10ms、単純Horner15.56ms、2系列8.17ms、4系列4.68ms。単純Hornerは乗算回数が少ないが、N=256以上で回帰した。4系列は0・1項で遅く、単一方式として採用せず小入力処理を加えた。

## 公開APIの比較

`api.cpp.snapshot`が公開ヘッダそのものを使う測定器。`baseline.hpp.snapshot`は変更前のHEAD、`candidate.hpp.snapshot`は最終案。係数と評価点は実行時seed 20261117で生成し、出力配列の全値を実行後のhashに含める。各実行の最初の20点は、独立の冪逐次計算とも直接照合する。乱数入力の生成・直接照合・hash計算は計時外。結果配列への格納は両方に含む。各条件warmup 1回、7回を交互に実行し、全出力hashが一致した。`api-results.json`に全生値、ソースhash、環境、回数、各条件の点数を保存している。結果は計時中の共有端末の負荷を統制していない。

Windows、Unity Android NDK Clang 18.0.3、x86_64-pc-windows-msvc、gnu++20、`-O2 -DNDEBUG`の中央値:

空で100万回あたり約1.3ms、1項で約0.28msの回帰が残る。この空の差はコンパイラによるループ最適化の影響を含み、単一呼出しの遅延と同一視しない。小入力対策前の測定は`api-results-before-small.json`。なお2回の測定は別の時刻であり、別系列の差を精密な前後比較としない。GCC、Linux、入力分布別、メモリ消費は未測定。上位提出との差をこの結果から求めることはできない。

## 正しさ・再現

ランダムテストは長さ0、1、4・8・16・32・256前後、評価点0・1・2・乱数、998244353と素数17を、冪を用いた独立の式と比較する。旧・新ともWindows Clang GNU++20、O2、assert有効でseed 1・17・731を完了した。`build-api.log`にコンパイル結果を残す。ACLヘッダ由来のClang警告があり、エラー扱いにはしていない。WSLはアクセス拒否のためLinuxでの確認は行っていない。

再現する場合、`api.cpp.snapshot`を`.build/fps-eval-study/api.cpp`、`build-api.py.snapshot`を同ディレクトリの`build-api.py`、`run-api.py.snapshot`を`run-api.py`へコピーし、リポジトリ直下で実行する。ビルドscriptはその時点の`HEAD`を旧版、作業ツリーのヘッダを新版として取得し、特定のWindows SDK・Visual Studio・Unity Clangのパスを使う。別revisionでの再現は保存済みsnapshotに差し替え、利用環境に合わせてパスを修正する。`.build/fps-eval-study/api-results.json`が上書きされるため、比較前に保存する。試作は`grouped.cpp.snapshot`と`run-groups.py.snapshot`を同様にコピーし、対応するbinaryを`-O2 -DNDEBUG`で作る。判定できなかった測定を0として扱わない。
