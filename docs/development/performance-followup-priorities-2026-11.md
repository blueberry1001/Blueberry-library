# 性能調査の次の着手候補（2026-11）

既存の測定記録を読み、競技中の実用上のリスクと調査の必要性から順序を付けた。
この文書では新たな性能測定を行っていない。利用頻度の実測順位でもない。
Library Checkerの提出時間と別環境のローカル時間を割って倍率を作らない。
履歴上の測定は測定時の入力・コンパイラ・revisionに限って解釈する。

確認時のHEADは `123365f2738e3d883c566def538e2833f411c317`。
以下の2DとOrderedMapのヘッダは確認時に作業ツリー上の変更がなく、HEADのGit blobの
SHA-256はそれぞれ過去の測定記録にあるヘッダのSHA-256と一致した。Windowsの改行変換を
含む作業ファイルのbyte列とGit blobは区別する。この一致は同じソースを示すだけで、
現在の環境で同じ速度が出ることは保証しない。

## 1. Dynamic Fenwick Tree 2D

[2026-09-17の測定](https://github.com/blueberry1001/Blueberry-library/blob/main/benchmark/dynamic-fenwick-tree.md)は既にある。
GCC 13.3、`-O2 -DNDEBUG`、各5回の中央値で、旧実装／オンラインAVL版は
20,000四方の一様入力で328.24／356.47ms、100四方に集中する入力で69.49／54.22ms。
10⁹四方ではオンライン版973.45ms、オフライン版242.86msだった。
旧版は巨大入力で測定していない。後者の比較は更新座標を事前登録できるかが違い、
オンラインAPIと同等契約での速度差ではない。
構築・操作・破棄は合算、入力生成は計時外で、RSSも記録されている。

測定時の2DヘッダSHA-256 `402e676360cef0769e1ea935bdc43defcef4a16f056f302025d91ef884e6cf42` は
上記HEADと一致する。一方、現在の環境での再測定、Nyaan版との共通のオンライン条件での
比較、構築・更新・問い合わせ・I/Oそれぞれの費用の分離は、この記録にはない。
Nyaan版は外側の座標数に比例する領域を確保するので、巨大な未知座標に対応する
本APIと同じ初期化・メモリ保証は持たない。共通条件で比べつつ、その差を明示する。
外側の共通Fenwick経路を除く区間和は候補だが、効果は未測定である。

## 2. OrderedMap / OrderedSet の反復子消去

[2026-10-20の反復子測定](measurements/extra-fast-more/sets/README.md)では、
N=50,000の単調入力で `erase(pos)` が標準map/setより約8.7〜10.8倍、
処理全体では約1.28〜1.44倍遅かった。5回の中央値で、GCC・Clang、
順逆走査、消去後の結果照合も記録されている。
現実装は消去時にキーの探索・平衡化・次位置の再検索を行うO(log N)操作であり、
標準の償却O(1)の位置消去とは計算量が異なる。逆に大きな乱数入力の走査では
本実装が速い結果もあるため、全操作の優劣として一般化しない。

測定時の `ordered-map.hpp` SHA-256 `30a686b7a5185aef2052e94608d802dada79fc7dab9f1234bc84ff37758bc0cc` は
上記HEADと一致する。現在の環境での再測定や改善案の速度は未測定。
次は返却反復子と既存の失効条件を維持できる消去方式を検討し、単調・乱数・小規模・大規模で
消去単体と前後を含む全体時間、メモリ、走査性能を比較する。

## 3. Weighted Wavelet Matrix の構築

[初回測定](weighted-wavelet-matrix.md)はGCC 13.3、N=Q=40,000、3回、
固定された乱数分布で既存OfflineFenwickTree2Dと比較している。両者は更新指定などの
APIが異なる。この結果は他者の同等APIとの比較や全入力での優位を示さない。
[後続の調査](measurements/frequent-2026-10/research.md)には、入力位置へrankを直接書き戻して
N回の二分探索を省く候補があるが、その候補の性能は未測定とされている。

まず現行ヘッダを基準に構築・操作・RSSを分離し、小N、低種類数、重複、広い値域を測る。
値型は整数に限らないため、比較可能な型と現在の公開契約を維持する。
通常WaveletMatrixのrank直接書戻しは[別の測定](measurements/generic-performance/sequence/README.md)で
既に採用済みであり、その結果をWeighted版の実測値として流用しない。

## 4. 高速版 FPS の残差

[2026-10-20の測定](measurements/extra-fast-more/fps/README.md)では、N=500,000の
プロセス全体で高速版と上位提出に約2.5〜3.3倍の差があった。提出側は専用I/O、arena、
必要な半分の変換などを使っており、この倍率は同一APIのkernel単体の差ではない。
提案された各工夫の寄与も分離されていない。通常版の型・法の汎用性を維持し、
変換、確保、I/Oを個別に置き換えた比較から次の候補を判断する。

## 記録の扱い

古い候補表の再実装を避けるため、後続の測定と現行ソースを先に確認する。
例えばStaticRangeLISの共有scratchは[後続の測定](measurements/generic-performance/sequence/README.md)で
既に採用され、当時のGCC random構築は408.583→155.355msだった。
この値を今回のrevisionの新たな測定や、全ケースでの速度保証として扱わない。

新しい調査は比較する契約を先に書き、同じ入力・環境・compiler・flagsで、構築・操作・
I/O・メモリを可能な範囲で分離する。入力分布や更新比を変え、反復の中央値と生ログ、
source hashを保存する。失敗・未実行・未測定はゼロ秒や成功に置き換えない。

性能とは別の既存課題として、Dynamic Fenwick Tree のコピー代入は確保や値のコピーが
例外を送出した場合、サイズだけ先に変わる可能性がある。例外発生後の利用が必要な
用途では、一時コピー後に交換する方式と対応するテストを検討する。
