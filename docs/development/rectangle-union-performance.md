# Rectangle Union の性能調査

2026-11-17。変更前 `28ea289f71cf90deee5d54cec410b7ecc779e4fd` と、同じ整数座標・面積型の入力を受ける候補を比較した。公開 API、空入力、退化矩形、負座標、重複、接触を維持する。ACL に矩形和の面積を直接求める API はない。

Library Checker の検索では [131 ms の提出](https://judge.yosupo.jp/submission/403009)を確認したが、今回そのソースと同じ実行環境での時間は取得できなかったため直接比較していない。[maspypy](https://maspypy.github.io/library/ds/rectangle_union.hpp.html) は端点と元の番号をまとめてソートして圧縮済み番号を得る方式、[sotanishy](https://sotanishy.github.io/cp-library-cpp/misc/rectangle_union.hpp.html) は圧縮後の二分探索と最小被覆数を使う方式だった。両者の入力上の前提は本 API と一致しないため、参考として調査し、本実装は独立に作成した。

変更前は各矩形の両イベントで上下の端点をそれぞれ二分探索し、区間外の子にも再帰呼び出しを行っていた。採用案では端点を一度ソートしてイベントに圧縮後の番号を直接書き、探索対象と交差する子だけ更新する。端点の一時配列は木の構築前に解放する。0〜2 矩形は直接計算し、退化矩形では幅や高さの差を計算しない。2 矩形では、個別面積の和が最終面積より大きくなり得るので `area(a) + (area(b) - overlap)` の順で計算する。

## 計測

Windows 11、Intel64 Family 6 Model 183、Clang 18.0.3 (`--target=x86_64-pc-windows-msvc -std=gnu++20 -O2 -DNDEBUG`)。同一プロセッサの affinity mask `0x1` に固定し、各候補を交互の順番で新しいプロセスから実行した。各ケースはウォームアップ 1 回と記録 9 回。表は中央値と最小〜最大、単位 ms。入力生成は時間に含まない。各回の返り値とハッシュは全候補で一致した。

少数矩形の反復では先頭の左端を各回変更する。0〜2 矩形の候補は短いため、コンパイラ最適化や計測ループの影響が大きい。大きな入力でも時間の分散があり、特に 50 万矩形の標本標準偏差は変更前 98.78 ms、採用案 110.31 ms だった。全退化の測定範囲は重なり、差は判定しない。ランダム 50 万矩形のピーク working set の中央値は変更前 91,381,760 byte、採用案 79,171,584 byte。OS の working set はアロケータや実行環境に依存する。

各候補のソース、入力生成、実行手順、各回の時刻・時間・ピーク working set・結果は [`benchmarks/research/rectangle-union`](../../benchmarks/research/rectangle-union) に保存した。`run-rerun.py --build`、続けて `run-rerun.py` で同じ Windows ツールチェーンの比較を再実行できる。環境固有のツールチェーンパスはスクリプト冒頭で調整する。`results-rerun.json` が上表の記録で、採用案は variant 8、変更前は variant 0。`results-next.json` は別のコンパイル・テストとの重複可能性があるため採否に使わず保存した。初期の `results-v1.json` は返り値ハッシュの衝突に弱い設計だったため正答性の根拠に使っていない。

今回の JSON には候補ヘッダのハッシュを保存したが、driver と実行バイナリのハッシュ、コンパイラのバージョン出力は保存していない。そのため、保存した driver と実行時のバイナリの対応はハッシュでは確認できない。
