# StaticTopTreeの説明と構築処理の改善

2026年10月3日、StaticTopTreeの説明を改訂し、構築時の不要な処理を省いた。
SuffixAutomatonについても2案を比較したが、安定した短縮を確認できなかったため採用していない。
公開API、対応型、必要な代数条件、計算量は変えていない。

## 説明の改訂

[StaticTopTreeの説明]({{ '/blueberry/graph/static-top-tree.hpp.html' | relative_url }})を、
小さい総和の例から、3つの型と5つのコールバック、一次関数を使う木DPへ進む構成にした。
上下の合成順、light subtreeを閉じる処理、根の固定、単位元、答えの取り出し方を説明している。
コピー・ムーブを含む9つの公開操作の説明と、入力・寿命・計算量の条件も残した。

文章の見直しには、[yomiyasuの公開ガイド](https://github.com/nanaism/yomiyasu/blob/8d5abeebe2dd20c2db005deaddcc50be43c59c0a/SKILL.md)と、
同じリビジョンの技術文書・構文・語彙の指針を読んで使った。
技術の説明として文末をそろえ、指示語の対象を明確にし、重複する強調を減らした。
主張、条件、言い切りの強さは、実装と既存の説明に照らして確認した。
ガイドのインストールや付属スクリプトの実行はしていない。
参照した4ファイルのハッシュは`benchmark/results/static-tree-string-tuning/yomiyasu-provenance.json`に記録した。

2つの例は、それぞれ単独でコンパイルできる。
文書検査も、最初の例に加えて、完全な`int main()`を持つ後続の例を実行するようにした。
短いAPI断片は引き続き単独コンパイルの対象外とし、追加例の失敗が検査全体へ伝わることもテストした。
対象の完全なコード例は110個から111個になった。

## 採用した変更

StaticTopTreeの`balance()`では、要素が1つだけでも累積和の配列を確保していた。
その場合は元の要素を直接返す。再帰の途中でも、要素が1つなら重みの二分探索と空区間への再帰を省く。
以前も、この場合には新しい結合ノードを作っていなかった。
結合する木の形、ノード番号、コールバックの順序と回数は変わらない。
単独includeに必要な`<cstddef>`を明示し、使っていない`<functional>`を外した。

構築の上界はO(N log(N+1))、更新は最悪O(log(N+1))、メモリはO(N)のままである。
更新処理そのものは変更していない。

### 測定条件

比較元は`9c2914f6db8fde2c56e5aade4fcc40c15b75cad5`。
Linux、Intel Xeon Platinum 8573C、GCC 14.2とClang 19.1.7で測定した。
標準は`gnu++20`、最適化は`-O2`。`-DNDEBUG`あり・なしの結果を分けている。
共有ホスト上の測定なので、他の利用者の負荷やCPU周波数の影響は残る。

木は10万頂点、更新は20万回。鎖、星、二分木、ランダム木、ほうき型を用意し、
`uint64_t`とmod 998244353の一次関数DPを測った。
構築と`set`・`all_prod`の反復を分け、入力生成、起動、出力、破棄の時間は含めない。
入出力の高速化を比較する実験ではない。
各条件でwarmupを1回行った後、変更前後とコンパイラの実行順を交互にして5回測った。
入力と結果のハッシュを毎回比較し、確保回数とコールバック数は計時とは別の実行で数えた。

次の表は`-DNDEBUG`あり、mod 998244353の場合の構築時間の中央値で、単位はms。
表の各セルは変更前→変更後を表す。

| 木の形 | GCC 14 | Clang 19 |
| --- | ---: | ---: |
| 鎖 | 8.972 → 8.581 | 8.823 → 8.355 |
| 星 | 15.540 → 12.999 | 15.778 → 13.965 |
| 二分木 | 16.257 → 13.027 | 16.965 → 13.601 |
| ランダム | 28.285 → 26.805 | 29.276 → 26.423 |
| ほうき型 | 11.599 → 9.712 | 11.802 → 11.549 |

`uint64_t`も含むreleaseの20条件では、構築時間の中央値が2.1〜28.4%短くなった。
ただし、assert有効の最初の測定では、GCCの二分木・`uint64_t`で11.8%、
Clangの鎖・`uint64_t`で9.2%長くなった。
Clangのほうき型・modintでは、更新時間の中央値も9.5%長かった。
これらを隠さず、同じ実行ファイルを使って対象3条件を9回ずつ追加測定した。

追加測定では、上の構築2条件はそれぞれ11.1%、9.5%短くなり、
更新の条件も3.3%短くなった。元の3つの悪化は再現しなかった。
一方、追加測定のGCC・鎖・`uint64_t`では構築が3.6%長く、測定範囲は大きく重なっていた。
小さな時間差を一律の改善とは扱わず、元の測定と追加測定を両方保存している。

確保回数の削減は両方のコンパイル条件で確認できた。
星では300,060回から200,062回、二分木では381,663回から306,664回、
ランダム木では342,347回から301,439回、ほうき型では150,091回から100,092回になった。
鎖は61回のままで、再帰内の省略だけが適用される。
更新時の確保は変更前後とも0回で、コールバック数も一致した。
ここで数えたのは確保要求の回数であり、同時に生存するメモリの量ではない。
RSSには入力配列なども含むため、構造単体のメモリ削減率は主張しない。

### 採用しなかったSuffixAutomatonの案

20万要素の4文字・26文字ランダム列、周期列、全同値列、整数列を用意した。
構築、初回の出現回数集計、2万回の照会、最長共通部分文字列を分けて測った。

| 候補 | 観測したこと | 判断 |
| --- | --- | --- |
| 複製した状態を`std::move`で格納する | 4文字ランダム列では139,033回の確保を省けたが、GCCの26文字列では構築が7.6%長かった | 安定した時間短縮を確認できず、不採用 |
| `contains`と`emplace`を`try_emplace`にまとめる | releaseのGCCでは26文字列・整数列で短縮したが、Clangでは4文字列・26文字列・全同値列がそれぞれ9.5%、7.7%、8.6%長かった | assert有効でも結果が混在し、不採用 |

確保や検索を減らす案でも、この測定では一律に速くなるとは確認できなかった。
SuffixAutomatonの公開ヘッダは変更していない。
最初のrelease実験は1つの実行ファイルに木と文字列の候補を含む。
後続の実験では対象ごとに変更を分離し、他方のヘッダを変更前後で同じにした。

## 検証と再現資料

StaticTopTreeのランダムテストは、普通の根付き木DPを毎回計算する独立した比較器にした。
根と頂点番号の変更、隣接リストの並べ替え、構築直後の答え、単頂点、繰り返し更新、
入力配列の寿命、コピー・ムーブ後の独立性を確認する。
根を2とする鎖の答え`41 → 56 → 131 → 330`も固定テストにした。
既存の10万頂点の鎖・星・二分木と、更新時のコールバック数の検査も残している。

全体の`make check`と、GCC/Clang・C++20/23の対象別検証の結果は、
`benchmark/results/static-tree-string-tuning/validation.json`に記録する。
対象別検証には、単独・重複include、assert有効・無効、乱数シード1〜20、
2つの文書例、ASan/UBSan、公式checkerによる78ケースの3回実行を含める。
公式データは以前取得したキャッシュとハッシュが一致し、ネット取得を必要としない。

対象別の結果は、乱数テスト160回、ヘッダ32構成、verifyのコンパイル12構成、
文書例8構成、ASan/UBSan・leak検査4回がすべて成功した。
公式テストも、StaticTopTreeの26ケース、最長共通部分文字列の28ケース、
部分文字列数の24ケースを各3回実行し、234回すべてACだった。

最初の公式テスト起動は、検証ツールがシンボリックリンクの入力を受け付けず、ケース実行前に失敗した。
失敗した報告は残し、同じハッシュのデータを実ファイルとして配置して、公式テストだけを再実行した。
再開時には、先に検証した実行ファイルとソースのハッシュも確認している。
最初の報告を成功に書き換えてはいない。

これは全件の公式検証が完了したという意味ではない。
前の統合検証で残ったAOJ `ALDS1_14_B`のデータ取得制限は解消しておらず、
元の失敗報告と公開判定を保持する。`make docs`の公開用メトリクス検査を省略した成功報告は作らない。
この作業ではpush、mainへのmerge、deployは行っていない。

測定器は`benchmark/static-top-tree-sam.cpp`と、同じディレクトリの各Pythonスクリプト。
結果は次のディレクトリにあり、変更前後のヘッダ、差分、コマンド、バイナリのハッシュ、
全サンプル、集計、確保回数を保存している。

- `benchmark/results/static-top-tree-sam/`：最初のrelease比較と状態コピー案。
- `benchmark/results/suffix-automaton-insertion/`：検索をまとめる案のrelease比較。
- `benchmark/results/static-top-tree-assert/`：木だけを変更したassert有効の比較。
- `benchmark/results/suffix-automaton-insertion-assert/`：検索をまとめる案のassert有効の比較。
- `benchmark/results/static-top-tree-assert-recheck/`：同じバイナリによる9回の追加測定。

通常の比較は`prepare`、`check`、`run`、`allocations`の順に実行する。
結果を上書きしない設計なので、再現時は元の結果を保存してから、別の作業用コピーで実行する。
GCC・ClangとACLのinclude環境を用意し、他のコンパイルやテストが動いていない状態で次を実行する。

```bash
for experiment in static-top-tree-sam suffix-automaton-insertion static-top-tree-assert suffix-automaton-insertion-assert; do
  for action in prepare check run allocations; do
    python3 "benchmark/$experiment.py" "$action"
  done
done
python3 benchmark/static-top-tree-assert-recheck.py
```

最後の追加測定は引数なしで実行し、assert有効の実験で作った変更前後のバイナリを再利用する。
