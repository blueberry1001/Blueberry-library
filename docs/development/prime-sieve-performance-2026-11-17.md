# PrimeSieve の構築高速化（2026-11-17）

`PrimeSieve` の判定表は全値を格納したまま、偶数の消去後に奇数の合成数だけを消し、素数一覧も奇数だけを走査する。判定のインデックスと一覧の参照 API、計算量は変えていない。確保時の `limit + 1` と `limit()` は `INT_MAX` でも符号付き整数の範囲外を経由しない形にした。

## 参考実装と契約

[Nyaan の prime_enumerate](https://nyaannyaan.github.io/library/prime/prime-enumerate.hpp.html) は 2 と 3 の倍数を除いた表から素数を列挙する。[Nachia の提出 #77249](https://judge.yosupo.jp/submission/77249) は奇数の表と素数一覧を段階的に拡張する。#77249 は 2134 ms と表示されたが、最速順位は確認できていない。提出先の [Enumerate Primes](https://judge.yosupo.jp/problem/enumerate_primes) は N ≤ 5×10^8 で一覧の一部を出力する問題であり、任意の `is_prime(x)` と一覧への参照を提供する本 API と契約が異なる。提出時の時間やメモリと以下の計測を直接比較できない。ソースは参考として読み、実装は独自に書いた。

[adamant の高速提出 #336744 の解説](https://codeforces.com/blog/entry/149218) は、執筆当時の最速として 83 ms・25 MiB を報告している。210-wheel で候補を圧縮し、小さい素数には SIMD で複数のマスクを適用し、大きい素数には区間分割と周期的な差分を使う。問題の出力向けの実装であり、全値の直接添字による `is_prime(x)` と素数一覧の参照を維持する本 API と条件が異なる。現在の最速順位と、本実装との同一入力・環境での性能差は未確認である。

奇数だけを `vector<bool>` に格納する候補も比較した。構築時間と判定表のメモリを減らせたが、ランダムな任意値判定で大きく遅くなったため採用していない。全値の bit 表を維持する案は構築が短縮し、判定の処理を維持できた。

## 同条件の測定

Windows 11、Intel64 Family 6 Model 183 Stepping 1、Clang 18.0.3、`--target=x86_64-pc-windows-msvc -std=gnu++20 -O2`。旧版と変更後は別々のバイナリで、同一入力・コンパイラ・フラグ・CPU affinity 0x1 を使った。旧版 SHA-256 は `38775f4a847975f65b116fa9d6c9f42e614e783b009964f1869d2f43011fd8a6`、変更後は `ae02bf488425ff3327834c5fd658bf36f29ce80a5baa620be0c41cf1661012e0`。

入力の生成と出力のチェックサム計算は計時区間外。初回を除く 7 試行の中央値を示す。構築は N < 10^7 では 1 試行につき 3 回、N = 10^7 では 1 回。乱数判定は固定 seed `20261117` の 200 万件を 2 回ずつ調べる。判定は混合、偶数、奇数の 3 分布を測った。全てのケースで各実装のチェックサムは一致した。

| 操作・条件 | 旧版中央値 | 変更後中央値 | 変更後 / 旧版 |
|---|---:|---:|---:|
| 構築 N=1,000、3 回、release | 0.0147 ms | 0.0120 ms | 0.816 |
| 構築 N=100,000、3 回、release | 0.8999 ms | 0.6262 ms | 0.696 |
| 構築 N=1,000,000、3 回、release | 8.3596 ms | 5.4927 ms | 0.657 |
| 構築 N=10,000,000、release | 26.9266 ms | 16.9940 ms | 0.631 |
| 乱数判定 N=1,000,000、400 万回、release | 1.2301 ms | 1.3711 ms | 1.115 |
| 乱数判定 N=10,000,000、400 万回、release | 1.8278 ms | 1.7349 ms | 0.949 |

assert 有効時の構築時間は旧版比 0.568〜0.824、判定時間は 0.968〜1.048。release の全判定分布は 0.936〜1.115 だった。判定は release で同じ配列へのアクセスだが、計測には変動があり、今回の結果から小さい差を一般化できない。全試行の値と最小値、assert 有効・無効の各結果はログを参照する。

N=10^7 の試行 1 のプロセスのピーク working set は旧版・変更後とも 10,108,928 bytes、奇数のみの候補は 8,101,888 bytes だった。working set には実行ファイルや素数一覧も含まれるため、表単体の容量ではない。採用案の表は旧版と同じ N+1 bit、奇数のみの案は概ね半分である。素数一覧のメモリは両方に必要である。

## 正しさと境界

公式対応は既存の `verify/math/enumerate-primes.test.cpp`。今回追加した `tests/random/prime-sieve.cpp` では、0〜300 の全上限、511/512/513・1023/1024/1025・4095/4096/4097・65535/65536/65537・100000、固定 seed の乱数上限に対し、各値を独立した試し割りと照合する。素数一覧、`limit()`、一覧参照、コピーとムーブも確認する。

Clang 18、C++20/23、assert 有効・無効の各組み合わせで seed 20261117・1・42 を実行し、全て成功した。計測コードでも 0〜300 とビット境界付近を試し割りと照合した。`INT_MAX` の実サイズ構築は、必要なメモリと時間が大きいため実行していない。上限加算は `size_t`、平方と倍数は `long long`、列挙は `size_t` で評価しており、値を `int` に変換するのは `limit` 以下の素数のみである。メモリ確保が可能である保証にはならない。

この Windows 環境の PATH に `make` と GCC がないため、`make test`・`make verify`・`make docs` と GCC での検証は実行していない。公式問題の制限時間内の完走も今回測定していない。
