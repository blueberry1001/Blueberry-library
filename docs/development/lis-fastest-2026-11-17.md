# LIS 高速化の調査（2026-11-17）

既存の `longest_increasing_subsequence` の変更は見送った。昇順では有力な改善があったが、値の種類が少ない入力では回帰し、周期入力では試行間で結果が逆転した。最速提出の制約と汎用 API は異なるため、そのまま置き換えない。

## 上位提出との比較

2026-11-17 の検索可能な順位表示では [#372659](https://judge.yosupo.jp/submission/372659)、[#372657](https://judge.yosupo.jp/submission/372657)、[#238857](https://judge.yosupo.jp/submission/238857) がいずれも 10 ms と表示された。順位や実行時間は変わり得る。#372659 のソースを確認したところ、入力と末尾配列は `uint32_t` で、末尾より大きい場合の直接追加、分岐を抑えた二分探索、位置ごとの LIS 長からの逆走復元、専用の高速 I/O を使っていた。提出に表示された最大ケースの時間であり、以下の Windows 上の関数単体測定とは直接比較できない。他の 2 件は順位表示のみを確認した。

現行 API は `const std::vector<T>&` と `<` を使い、値をコピーせず添字を返す。任意の整数型やユーザー定義型を扱うため、符号なし固定・値配列へのコピー・専用 I/O は採用しない。今回の候補は添字を保存したまま各処理を試し、現行と同じ添字列を返すことを比較対象とした。ACL に対応する LIS 関数はない。

## 計測方法

Windows 11、Intel64 Family 6 Model 183 Stepping 1、Clang 18.0.3、`--target=x86_64-pc-windows-msvc -std=gnu++20 -O2 -DNDEBUG`。CPU affinity は 0x1 に設定した。元ヘッダの SHA-256 は `052dae4f29cb583201d6b0af2c49920bc3bad599339328528753485435ff7189`。I/O を除いた API 全体を計時し、入力生成・結果照合は計時区間外である。N = 200,000、固定 seed `20261117`、各プロセス内で 3 回または 6 回実行し、初回を除く複数試行の中央値と最小値を記録した。候補の実行順は試行ごとに反転した。

乱数、昇順、降順、全同値、8 値の乱数、1000 周期の昇順、ほぼ昇順の 7 分布を使用した。各実行で候補と現行の返却添字列を直接比較し、全ケースで一致した。これはこれらの入力に限る比較であり、公式 verify や汎用型の網羅的な正しさ検証ではない。API、計算量、実装には変更を加えていない。
