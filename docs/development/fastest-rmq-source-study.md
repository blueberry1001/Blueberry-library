# Static RMQのFastest提出から分かる実装上の差

Library Checkerの公開v3 REST APIから、2026年9月19日06:52 UTCに取得したソースを調査した。このページは実装の読解結果であり、ローカルの速度測定結果ではない。公開時間はテストケースの最大実行時間であり、提出間でコンパイラの版・実行機の履歴・測定の揺らぎまで一致するとは限らない。120 msと20 msという結果だけでは、データ構造・構築・入出力それぞれの寄与は分からない。

**改善では既存の汎用性と使いやすさを維持する。** 以下のmin専用処理、固定された入力形式、SIMD、クエリの一括処理は、速い提出との違いを説明する材料として扱う。それらを理由に、任意のモノイドに対応するSqrt Treeや、比較器・左端argmin・線形構築を保証するLinearRMQを狭い用途の実装へ置き換える方針ではない。

## 共通するアルゴリズム

共通点は、**小さな固定幅ブロックと、ブロック全体の最小値に対するSparse Table**である。幅B=16とし、各位置にブロック内のprefix／suffix最小値を持つ。複数ブロックをまたぐ問い合わせは、左端suffix・右端prefix・中間の完全なブロックを覆う2個の表要素を結合する。同一ブロック内なら最大16要素を走査する。

中間の表要素が重複するため、結合則に加えて冪等性を必要とする。区間和や行列積を含む一般モノイドのSqrt Treeの代替にはならない。提出ではunsigned整数のminを使用している。

構築・記憶量はO(N + (N/B) log(N/B))、問い合わせは同一ブロックでO(B)、ブロックをまたぐ場合O(1)。Bを固定定数とすれば問い合わせは定数時間だが、**Nを増やしたときの構築が厳密に線形になるわけではない**。B=16の除算は定数シフトにできる。上位表の横幅は通常のSparse Tableの約1/16になり、prefix／suffixからは値を直接得るため、添字を取得して元配列を参照する処理も不要になる。

20／21 msの3件では、上位表は各段に必要な長さだけ確保したvectorの集合である。入力値はコールバックから直接構築するため、呼び出し側の入力vectorを別に用意しない。短区間の処理は走査であり、Cartesian Treeのbitmask RMQではない。SIMD intrinsicは使わず、GCCの最適化レベル3を指定している。この事実は、速さの全てを明示的SIMDに帰すこともできないと示している。

19 msの402567では、同じ方式に次の工夫が加わっている。

- 上位表を段ごとの有効長で単一配列に配置し、単位元だけの行も持つ。隣接ブロック間の問い合わせを通常の経路で処理でき、形状による分岐が1つ減る。一方で、その行の記憶量とロードが増える。
- prefix／suffix構築、上位表の8要素ずつの結合、同一ブロック内の最小値計算にAVX2を使う。短区間用関数は意図的にinlineしない。ここでのmaskはSIMD lane選択用で、単調stackのbitmaskではない。
- 8クエリをまとめて読み、評価し、出力する。`fold_batch`自体はscalarな問い合わせを繰り返すfor文であり、8 laneのgatherによるRMQではない。独立処理を並べられることや、入力・出力位置管理の共通化が測定候補になる。
- ブロック境界までの容量を確保した入力vectorを、構築先へmoveする。

402567のソースはAVX2実行を選択しているが、GCCのtarget pragmaは含まない。再現には適切なコンパイラとISA設定が必要であり、APIの言語タグだけから有効なコンパイル引数一式は断定できない。

## 入出力による差

20／21 msの3件は、Unixの通常ファイルに対するmmap、4／8桁のSWAR整数変換、4桁単位の出力テーブルとfwriteのバッファ出力を使う。区間の添字には値より短い入力処理を選ぶ。mmap経路ではトークンごとの境界確認を省き、正しい数値形式と先読み領域を前提にする。コンパイル時のfread代替経路はあるが、Unixでpipeやmmap失敗に遭遇して自動的に切り替える実装ではない。

402567はLinuxの前後padding付きmmap、AVX2の区切り文字検出、複数フィールドの整数変換、POSIXのバッファ出力を使う。入力件数・桁数が既知であること、先頭位置にある通常ファイルのstdin、4 KiBページを前提とし、pipeへの代替処理はない。添字は6桁以内に特化し、出力は全バイトを書き込めることを仮定している。

これらの環境・入力形式の制限を、一般用途のI/Oへそのまま持ち込まない。まずはpipe、符号付き整数、EOF、バッファ境界を扱える通常のfread／fwrite方式を同じ条件で測定する。mmapやSIMDは速い提出の差を理解するための比較対象であり、今回の優先実装ではない。

Blueberryの現行Sqrt Tree RMQ verifierは同期を無効化したcin／coutを使う。同期ありより改善されていても、参照提出とは異なる数値変換処理である。**入出力だけを交換した比較をせず、公開時間の比率を全てSqrt Tree本体の遅さに帰すことはできない。**

## Blueberryの現行実装と、保証を保った測定仮説

| 実装 | 維持する保証 | 測定する定数倍の要因 |
| --- | --- | --- |
| SqrtTree | 任意の結合的モノイド、非可換演算の順序、O(1)問い合わせ | 各階層の3配列とpadding、構築時の値コピー・単位元初期化、階層選択、依存するアドレス計算 |
| LinearRMQ | word-RAMで厳密なO(N)構築・空間、左端argmin、任意の比較器 | N依存のブロック幅による変数除算、添字から値への間接参照、同値判定の比較回数、上位表の配置 |
| SparseTable | 冪等な結合的演算、非空区間の2要素結合 | 既に単一配列・有効長のみの配置。構築時の初期化とコピー、オフセット参照、N log N要素のcache負荷 |

LinearRMQの幅をNと無関係な定数に固定し、上位にSparse Tableを置いたままでは、厳密な線形構築という保証を失う。一方、log Nに比例する範囲で幅を2の冪に丸め、シフト演算にできるようにする案は、その保証を保てる測定仮説になる。幅の上下限、wordのbit数、空配列・境界サイズも合わせて確認する必要がある。

最小値だけを返す実装と、左端のargminを返す実装も異なる契約である。同値処理を消すのではなく、候補の添字順などが証明できる箇所で比較を減らせるかを調べる。比較器に新たな制限を課さず、非標準の型や等価な値でも結果を維持する。

構築のmove対応、内部配列の連続配置、再確保の削減、直後に上書きする初期化の削減は、汎用性を維持しやすい候補である。ただし、一般のS型が持つ構築・代入・破棄の意味を無視したraw memory操作は避ける。計測で有効性が確認できたものを採用し、既存のconst vectorからの構築や単一クエリAPIは維持する。

## 測定と改善の順番

1. 同じコンパイラ・引数・公式入力・実行方法・出力検証で、全体時間の基準を作る。ソースhashと各試行のログを保存し、反復の中央値と最小値を報告する。失敗や未測定を0扱いしない。
2. アルゴリズムとI/Oを別々に交換する。Sqrt Tree、Sparse Table、LinearRMQなどを同じstream I/Oと同じ汎用バッファI/Oで比較する。入力済みデータ上での構築・問い合わせも分離し、checksumを照合する。専用blocked tableは差の説明用の参照点に留める。
3. 短区間・長区間・混合、単調・同値・ランダム、ブロック境界をまたぐ入力を使う。RMQだけで判断せず、Sqrt Treeでは非可換モノイドや大きな値型、LinearRMQでは比較器と同値のargminも確認する。構築を含む総時間と最大メモリを残す。
4. 配列配置、コピー、allocation、再確保、変数除算、重複ロードの順に調べる。assemblyで実際の除算やinlineの状態を確認し、1項目ずつ変更して比較する。小さな結果の揺らぎは改善と断定しない。
5. SIMD、固定桁入力、batch化を外した状態でも改善するかを確認する。これらを利用者の必須条件にしたり、オンラインで次のクエリが決まる通常の使い方を失わせたりしない。外部の最速提出との差として残る部分は、対応範囲の違いを説明する。
6. 同じAPI・代数的条件・更新要件を満たす実装間で改善を評価する。問題に必要な機能より広いAPIであることは速度差の理由になり得るが、既存の遅さを放置する理由にはせず、汎用性を保った実装上の無駄を先に減らす。

以上はソースに基づく測定仮説である。公開された19／20／21 msだけから、各工夫の効果量やAVX2の必要性を断定しない。
