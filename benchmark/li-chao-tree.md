# Li Chao Tree の方式比較

## 調査と採用理由

2026-09-14 に [Nyaan の座標圧縮方式](https://nyaannyaan.github.io/library/segment-tree/li-chao-tree.hpp) と
[Luzhiled の動的整数座標方式](https://ei1333.github.io/library/structure/convex-hull-trick/dynamic-li-chao-tree.hpp.html) を調査した。
コードは転載せず、直線が高々1回交差する性質を使って独立に実装した2候補を比較する。

| 方式 | 構築 | 直線 / 線分追加 | 取得 | メモリと用途 |
| --- | --- | --- | --- | --- |
| 座標圧縮・配列（採用） | O(M log(M + 1)) | O(log(N + 1)) / O(log²(N + 1)) | O(log(N + 1)) | O(N)、座標先読みが必要、更新中に allocation なし |
| 整数座標・動的ノード（比較） | O(1) | O(log V) / O(log² V) | O(log V) | 必要ノードだけ確保、座標を先読みしない |

M は入力座標数、N は重複除去後の座標数、V は整数座標領域の幅。動的方式のノード数の粗い上界は
Q 回の線分追加で O(Q log² V)、有限領域を全展開した場合 O(V) である。
動的方式は `unique_ptr` でメモリを所有し、両方式とも空の直線を optional で区別する。
採用実装は登録座標だけで演算するため、数値幅や末尾パディングの加算に依存しない。
現代的な最小値・線分 API を追加する目的で配列方式を採用し、オンライン用途に使う旧
`blueberry/ConvexHulltrick.hpp` は互換性のため変更しない。

## 再現

リポジトリルートから Linux / WSL 上で `python3 scripts/run_li_chao_benchmark.py` を実行する。
GCC と `/usr/bin/time` が必要。ソースは `benchmark/li-chao-tree.cpp`、全反復の標準出力・RSS・時間を
`benchmark/results/li-chao-tree-2026-09-14.json` に保存する。失敗時は非ゼロ終了し、欠測を0としない。

- Intel Core i7-14650HX、Ubuntu 24.04 / WSL2、GCC 13.3.0。
- `-std=c++20 -O2 -DNDEBUG -Wall -Wextra -Werror -I.`、各候補同じ条件。
- seed 1729、100,000 回の追加と直後の取得、計 200,000 操作。
- 座標は整数 `[-1000000, 1000000]`、同じ生成済み操作列を両候補に与える。
- 直線は乱数 c に対して `a = -2c, b = c²` とし、多数の直線が最小値になりうる下包絡線を作る。
- 線分 workload は同じ直線にランダムな半開区間を付ける。空区間も許す。
- 入力生成は測定外。座標コピー・ソート・初期確保を含む構築と操作を測定し、デストラクタは時間測定外。
- 候補ごとにウォームアップ1回、5回直列実行。両候補の全取得値のハッシュが一致することを検査。
- peak RSS は入力配列、ライブラリ、プロセス全体を含み、構造単体のメモリではない。

## 結果

| workload | 候補 | 中央値 ms | 最小 ms | 中央 peak RSS KiB |
| --- | --- | ---: | ---: | ---: |
| 直線 | 座標圧縮 | 39.730 | 39.419 | 18800 |
| 直線 | 動的 | 25.334 | 24.832 | 12344 |
| 線分 | 座標圧縮 | 67.391 | 66.413 | 18788 |
| 線分 | 動的 | 133.938 | 115.340 | 49180 |

今回の線分 workload は配列方式が速く、RSS も小さい。一方、直線のみでは動的方式が速くメモリも小さい。
よって配列方式の一律な高速性は主張しない。測定は2つの入力分布だけで、オンライン入力や極端に疎な
クエリへの優位性を意味しない。WSL と同時実行プロセスの負荷による揺れは全反復ログに残している。
今回の測定中は他のビルド・テストも進行しており、無負荷・CPU専有環境の測定ではない。
Library Checker 上の表示時間とは測定条件が異なるため比較しない。
